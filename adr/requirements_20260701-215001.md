The retail bank data catalog has three lines of business with varying levels of completeness:

- Missing: test data files (`testdata/*.jsonl`) for all tables

**Root ontology** (`ontology.sqrl`) — INCOMPLETE:
- Imports customer and lending ontologies but NOT deposits & payments
- Defines Customer-to-Lending relationships but NOT Customer-to-Deposits/Payments relationships
- Missing: `/*+test */` snapshot verification queries

**Test infrastructure**: `ontology-test-package.json` exists and is configured for Flink streaming.

## Requirements Summary

Complete the finance data catalog so that all three LOBs have: (a) properly structured schema definitions following the `_schema` convention, (b) environment connector files for test and prod, (c) unit ontology files with relationships and data quality assertions, (d) test data files with at least 5 records per table, and (e) the root ontology imports and relates all LOBs with verification test queries.

## Scenario Analysis

**Why catalog**: The project is a shared schema repository — `CREATE TABLE ... _schema` definitions, per-environment connector files, ontologies, test data — consumed by downstream pipelines. There is no pipeline transformation logic, windowed aggregations, or GraphQL API. This matches the `catalog` artifact type per the scenario taxonomy.

**Why extend-catalog**: Datasets, governance conventions, and README files already exist across three LOBs. The task is to bring all LOBs to parity, fill missing pieces (ontologies, test data, environment connectors), and wire cross-LOB relationships into the root ontology.

## Technical Decisions

- **Deposits & Payments naming pattern**: Use `dp_accounts_` prefix for test data file names (e.g., `dp_accounts_account.jsonl`, `dp_accounts_account_holder.jsonl`) to ensure global uniqueness, consistent with the `customer_master_customer.jsonl` pattern in customer domain.
- **Lending naming pattern**: Use `credit_cards_credit_card_account.jsonl`, `consumer_loans_personal_loan.jsonl`, `mortgage_originations_mortgage_application.jsonl`, `mortgage_servicing_mortgage_payment.jsonl` patterns.
- **Ontology table references in deposits_payments**: The ontology will reference the environment-resolved table names (e.g., `Account`, `Transaction`) not the `_schema` variants, consistent with how customer_ontology.sqrl works.
- **Silver datasets**: Silver datasets (account_analytics, enriched_transactions, credit_risk_signals, mortgage_performance) are derived and do not need their own test data — they are computed from bronze table test data. They do need `-test.sqrl` and `-prod.sqrl` files to define the source of their derivation.
- **Customer-enriched test data files**: Since `Customer_Profile`, `Customer_Segment`, `Customer_Household`, `Customer_Lifetime_Value` are silver/derived tables, they do not get their own `.jsonl` files. They are computed in the ontology from bronze data, not sourced from files/Kafka.

## Assumptions

- **Test data file paths**: Assumed test data connector paths follow the pattern `'${DATA_PATH}/<filename>.jsonl'` consistent with the `customer_master-test.sqrl` convention. [impact: high]
- **Watermark strategy**: For file-based test connectors, assumed watermark on `ingested_at` with a 10-second offset, matching the existing `customer_master-test.sqrl` pattern. [impact: medium]
- **Deposits & Payments Kafka topic names**: Assumed topic naming follows `dp_accounts.account`, `dp_accounts.account_holder`, `core_transactions.transaction`, `card_transactions.card_authorization`, `ach_transactions.ach_transaction` etc. pattern for prod connectors, consistent with `customer_master.customer` pattern. [impact: medium]
- **Primary keys and partition keys**: Assumed no explicit `PRIMARY KEY` or `PARTITION KEY` on file-based source connectors, matching the existing `customer_master-test.sqrl` pattern. Prod Kafka connectors will use appropriate keys. [impact: low]
- **Cross-LOB customer_id alignment**: Assumed the same `customer_id` values are used across Customer, Deposits & Payments, and Lending test data to enable cross-LOB ontology relationships to resolve. [impact: high]
- **Deposits ontology scope**: Account analytics tables (Account_Activity_Summary, Account_Balance_Trend, Dormancy_Signal) are silver/derived and will NOT be directly imported in the deposits ontology — their upstream tables (Account, Account_Balance_Daily, Transaction) are what get related. [impact: low]
- **Silver dataset connector files**: Silver dataset `-test.sqrl` / `-prod.sqrl` files will define derived tables as compute nodes (not LIKE-a-schema), consistent with the pattern that silver datasets are computed, not ingested. [impact: low]
